# Kale

Central authentication/authorization service plus a thin shared client package.
Full spec: [docs/DESIGN.md](docs/DESIGN.md). Approved decisions on its open items are below.

## Stack
- .NET 10 (SDK pinned in `global.json`), C#, ASP.NET Core
- OpenIddict (OIDC/OAuth server) + ASP.NET Core Identity
- PostgreSQL via EF Core + Npgsql (`timestamptz` everywhere)
- gRPC between client apps and AuthService (`Auth.Contracts` holds the `.proto` files)
- Cache-invalidation events: outbox table + PostgreSQL LISTEN/NOTIFY between AuthService instances, gRPC server stream to client apps (no message broker)
- Podman + podman-compose only (no Docker). Host is Apple Silicon (arm64)
- Tests: xUnit + Shouldly (+ Testcontainers on Podman)
- Admin UI (Phase 7): Next.js BFF, Turkish + English

```bash

./scripts/smoke-test.sh       # end to end against that stack: real sign-in, allow/deny by role, role edit via the invalidation stream (needs jq)
./scripts/publish-client.sh <feed>   # publish the packages (Contracts, Client, Web, Desktop) at <VersionPrefix> to a NuGet feed (API key on stdin; a folder works too); a version already there is refused
./scripts/register-app.sh <key> [--web <address>] [--desktop] [--new-secret] <project>...   # connect an application to the local Kale: registers it, writes Kale:* (incl. the secret) into the projects' user secrets; --desktop also turns on desktop sign-in; --new-secret writes a new secret (the old one keeps working for Applications:OldSecretValidFor)
./scripts/browser-test.sh     # admin UI in a real browser (Playwright, Chromium) against that stack; once per machine: (cd admin-ui && npx playwright install chromium)
podman compose down           # stop; add -v to delete the database volume: dev-stack.sh then recreates the sample application and its secret
dotnet run --project src/AuthService -- admin            # setup commands (create-application prints the client secret; create-user reads the password from stdin; set-password <user-name> too, the way back for a locked-out admin). dotnet run adds its own first line to stdout: scripts run the built dll or the container instead
(cd admin-ui && npm ci && npm test && npm run typecheck && npm run build)   # admin UI: unit tests, types, production build
dotnet pack src/Auth.Contracts -c Release -o ./packages && dotnet pack src/Auth.Client -c Release -o ./packages && dotnet pack src/Auth.Web -c Release -o ./packages && dotnet pack src/Auth.Desktop -c Release -o ./packages   # Kale.Auth.Client + Kale.Auth.Contracts + Kale.Auth.Web + Kale.Auth.Desktop for applications (docs/integration); raise <VersionPrefix> in Directory.Build.props first
dotnet ef migrations add <Name> --project src/AuthService --output-dir Persistence/Migrations
dotnet ef database update --project src/AuthService --connection "<AuthDb connection string>"  # design-time factory has no real DB
```

## Local environment
- `compose.yaml` takes every value from `.env` (copy of `.env.example`, git-ignored; `scripts/env.sh`, used by the dev scripts, appends keys added to `.env.example` later). Passwords and client secrets are Podman secrets mounted as files (`kale_postgres_password`, `kale_sample_client_secret`, `kale_admin_password`, `kale_admin_ui_client_secret`). Never put them in `.env` or compose.
- The compose stack is Development only (plain HTTP, h2c gRPC on `AUTHSERVICE_GRPC_PORT`, also published on `APP_BIND_ADDRESS` for an application run with `dotnet run`). AuthService's issuer is `http://auth.kale.localhost:${AUTHSERVICE_PORT}/`: `*.localhost` resolves to this machine in browsers and curl, and inside compose it's AuthService's network alias, with the same port inside and out, so tokens, discovery and JWKS URLs are the same for the browser and for SampleApp. `dev-stack.sh` tries to create the `sample` application on every run (the secret is printed only then): after a database reset it succeeds and replaces `kale_sample_client_secret`; otherwise the existing secret stays.
- `scripts/dev-db.sh` (for running AuthService with `dotnet run` instead) creates `.env` and the secret if missing, starts PostgreSQL, waits for its healthcheck, stores the AuthService connection string in .NET user secrets (Development only), and applies migrations.
- Images (`Containerfile` per deployable, context = repo root, `.containerignore`): SDK build stage, `aspnet:10.0-alpine` runtime as the built-in non-root `app` user (uid 1654) on port 8080, with `wget` for healthchecks against `GET /health` (anonymous). AuthService's image adds `icu-libs` and turns off invariant globalization: without it startup fails with `CultureNotFoundException` (TR/EN pages).
- Secrets reach the apps as files (mounted Podman secrets), never as environment variables: AuthService reads `AuthDb:PasswordFile` (added to `ConnectionStrings:AuthDb`); SampleApp reads `Kale:ClientSecretFile`. `AuthService admin migrate` brings the database up to date, needing only the connection string (it runs before any other setup), so a one-shot migration container holds no other secrets.
- podman-compose 1.6 can't mount an external secret under a different name, so the compose secret key equals the Podman secret name.

## Tests
- Database tests use a real PostgreSQL via Testcontainers (`PostgresFixture`, image `postgres:18-alpine`). Put them in `[Collection(UsesPostgres.Name)]`: one container is shared per collection, and each test gets its own fresh database from `CreateDbContext()`.
- Testcontainers reaches Podman through `~/.testcontainers.properties` (machine-specific, not in the repo): `docker.host=unix://<podman socket>` and `ryuk.disabled=true`. Get the socket from `podman machine inspect --format '{{.ConnectionInfo.PodmanSocket.Path}}'`. The Podman machine must be running.
- App-level tests start the real `Program` with `Hosting/AuthServiceApp.CreateAsync` (own migrated database, `Testing` environment, issuer `https://auth.kale.test/`, `FakeTimeProvider` as `Clock`). The app loads keys at startup, so any test that starts it needs a real database.
- `MigrationTests.Model_has_no_changes_missing_from_migrations` fails whenever the EF model changes without a migration. `ConfigurationValidationTests.The_apps_database_model_matches_the_migrations` does the same for the context built by the app's own DI, which catches model changes from app setup (e.g. Identity options).
- Test databases use `Pooling = false` (one database per test would otherwise exhaust PostgreSQL's connections).
- `EndToEnd.Tests` (collection `UsesContainers`: PostgreSQL): `SampleAppHost` runs the real `samples/SampleApp` (its `Program.cs` and `appsettings.json`) against the in-memory AuthService; `AuthServiceSteps` signs users in and waits for registration. `ClientApp` is a client app (`AddKaleAuth`, own `FakeTimeProvider`) whose backchannel goes to the in-memory `AuthServiceApp`; `Backchannel` counts or fails its calls. Client apps check token lifetimes with the real clock, so `AuthServiceApp.Clock` starts at the real time. `SampleWebHost` runs the real `samples/SampleWeb` (own `FakeTimeProvider`, to make its tokens look old without moving Kale's clock) against the in-memory AuthService and `SampleAppHost`; `WebBrowser` is a browser across both sites (one cookie jar, redirects followed, requests marked as page navigation or fetch). Web hosts use `AuthServiceApp.Issuer` as their Authority: Kale's discovery builds the browser's addresses from the request's host.
- Admin UI browser tests (`admin-ui/e2e/`, Playwright, `scripts/browser-test.sh`) run against the compose stack, in English, signed in as the first admin. They cover what plain form posts can't: forms after an action (React resets them), confirmation dialogs. Each test makes its own names (Playwright reloads the file after a failure). They aren't part of `npm test` (vitest, `test/`).
- If a new test passes on its first run, prove it can fail (break the code temporarily) before trusting it.

## Code conventions
- **KISS: write code a human can read and maintain.** Prefer the plain, obvious solution over a clever one, even if it's a few lines longer or a little slower. Optimize only for a measured need, and comment why. Avoid tricks such as casts to reuse an overload, dense LINQ chains, deep generics, reflection, or abstractions with a single user, unless the simple version is clearly worse. A new teammate should understand a method on first read.
- **Comment the why, not the what.** If a line wouldn't be obvious on first look (a workaround, a non-obvious constraint, a security or concurrency reason, a link to a DESIGN.md decision), add a short comment saying *why* it's there. Don't comment code that already explains itself.
- Standard .NET naming: PascalCase for types, methods and properties; camelCase for locals and parameters; `_camelCase` for private fields.
- Database names are snake_case (EFCore.NamingConventions). Ids are UUID v7 (`Guid.CreateVersion7()`); times are `DateTimeOffset` mapped to `timestamptz`.
- Entities with their own id inherit `BaseEntity` (`Id`, `CreatedAt`, `ModifiedAt`), and their configuration inherits `BaseEntityConfiguration<T>` (override `ConfigureEntity`). Pure join tables don't. `AuthDbContext.SaveChanges` sets the timestamps of every `IHasTimestamps` entity (`BaseEntity`, plus `User` and `UserApplication`, which can't inherit it) from the injected `TimeProvider`. Bulk updates and raw SQL bypass it, so they must set `ModifiedAt` themselves. In tests, pass a `FakeTimeProvider` to `PostgresFixture.CreateDbContext(clock)`.
- Entities live in `src/AuthService/Domain` as plain classes. Their EF mapping lives in `Persistence/Configurations`, one `IEntityTypeConfiguration` per entity, applied explicitly in `AuthDbContext`. Name constraints explicitly (`ck_…`, `fk_…_same_application`) so a violation says which rule fired.
- Users use ASP.NET Core Identity through `IdentityUserContext<User, Guid>`, so there are **no Identity role tables**: roles are our own per-application entity. Identity's tables are renamed to plain names (`users`, `user_claims`, ...) before our configurations run. Passkeys are off.
- `OnDelete(Restrict)` becomes `ON DELETE RESTRICT`, which reports SQLSTATE 23001 (restrict_violation), not 23503. Tests that check deletes at the database level call `ChangeTracker.Clear()` first, or EF applies cascade/restrict to tracked rows itself.
- Migrations in `Persistence/Migrations` are marked as generated code in `.editorconfig`, so analyzers skip them.
- The auth database provider is configured only in `AuthDatabaseOptions.UseAuthDatabase`, shared by the app, tests and `dotnet ef`.
- Row locks go through `Persistence/RowLocks` (one named method per lock, e.g. `LockUserForUpdateAsync`; the lock order that keeps them deadlock-free is written once at its top); advisory lock numbers live in `Persistence/AdvisoryLocks`. The caller comments why it takes the lock; who takes what is in `docs/design/locking.md`.

## Workflow
- **TDD.** For every behavior: write a failing test first and run it to see it fail for the right reason (red), write the minimum code to pass (green), then refactor with tests green. Show the real red and green output.
- **One branch = one feature** (one cohesive, reviewable change), never a whole phase. Name it `feature/<thing>`, `fix/<thing>`, `chore/<thing>` or `docs/<thing>`. Branch from up-to-date `main`; open one PR per branch.
- **Review loop:** fix every **blocking** and **should-fix** item from `pr-reviewer`. Fix nits only when they're cheap; otherwise reply saying why not. Re-run the reviewer **at most once** after fixes, and only if a blocking item was fixed. **Answer every inline review thread directly** (reply in the thread, not only in a summary comment): say what was fixed and in which commit, or why it won't be fixed, then **resolve** the thread. Use the GraphQL mutations `addPullRequestReviewThreadReply` and `resolveReviewThread`. Concerns that appear only in the review body get answered in one PR comment. Don't open separate PRs for small docs tweaks; batch them into the next related branch.
- **Merge `main` into the branch before opening (or updating) a PR:** `git fetch origin && git merge origin/main`, resolve conflicts, then re-run `dotnet build` + `dotnet test` and push. Several agents and people work in parallel, so a PR must be reviewed against the current `main`, not the one it started from. Merge, don't rebase, so pushed history isn't rewritten.
- The phases in DESIGN.md set the order of work only. Each phase is delivered as several feature branches. This changes only the **cadence** of two DESIGN.md working rules, from per phase to per feature branch: running the build and tests (still showing real output, see the last line of Rules) and committing (still with a clear message).

## Rules
- **Open source only.** Do not add MassTransit v9+, MediatR, AutoMapper, FluentAssertions v8+, Redis (use Valkey), or anything else with a non-OSS license. Flag license doubts before adding a package.
- **Podman only.** `Containerfile` per deployable (multi-stage, non-root), rootless, Podman secrets for passwords/client secrets, no hardcoded ports/hosts (`.env.example`).
- Cross-application integrity is enforced by **database constraints** (composite FKs), not only code.
- Operation names are stored as `"{appKey}.{EnumMember}"` strings, never enum integers.
- Access tokens carry `sid`, user id, expiry, audience. No operations.
- **Show real output, not "it compiles".** Every PR description includes the actual `dotnet build` result (warnings/errors) and `dotnet test` result (passed/failed/total) from the final run on the branch.

## Decisions on the spec's open items
- No message broker (owner's decision; RabbitMQ was used first and has been removed): client apps get their events over gRPC (`InvalidationStream`, below) and Kale's instances share them through PostgreSQL LISTEN/NOTIFY.
- Admin model: one superadmin level. AuthService registers itself as Application `auth` with operation `auth.Admin`.
- Operation registration survives rollouts (`OperationRegistrar`): each operation records `last_registered_at`; a registration adds or reactivates what it lists and marks obsolete only operations no registration has listed for `Operations:ObsoleteAfter` (default 30 min, at least 15 min = three client rounds, `OperationRegistrationSettings`), so during a rolling deployment, a restart of an old instance or a rollback both versions' operations stay active, and the old extras lapse on their own. No version numbers. Existing rows got the migration's time. Reactivations, obsoletions and changed implications queue `RoleEdited` for every role of the application in the same save (a new operation alone changes no role); an unchanged re-registration writes only the timestamps and queues nothing.
- Groups are flat (no nesting). No enum rename support (a rename creates a new operation; the old one becomes obsolete).
- Operation implications: `[Implies(...)]` on an enum member (`Auth.Client/ImpliesAttribute.cs`) is sent with registration and stored in `operation_implications` (same application; a registration replaces the implications of the operations it lists and keeps the others, so each follows the latest registration listing it); registration refuses loops (`OperationImplications.FindCycle`, `INVALID_ARGUMENT`). A role's effective operations (`EffectiveOperations`) are its grants plus everything they imply, through chains, leaving obsolete operations out (neither granted nor followed).
- Audit: hooks only (domain events through the outbox); no audit table yet.
- Sign-in requires an active `UserApplication` row. Gaining a role creates it when there is none (`Users/AccessWithRole`, in the same transaction): `UserAccess.AssignRoleAsync`, `GroupEditor.AddMemberAsync` (each application the group has roles in) and `GroupEditor.AddRoleAsync` (every member). An existing row is never changed (access an administrator turned off stays off), and taking a role away leaves access alone. Only the `assign-role` setup command also turns access back on (recovery).
- An operation's `{appKey}.` prefix is enforced by the database: `operations.(application_id, application_key)` references `applications(id, key)`, plus a `starts_with` check. As a result `Application.Key` can't change once operations use it.
- Sessions: 8 h absolute lifetime (configurable); access tokens last 10 min, and every refresh re-checks that the session is active. `Session.EndedAt` is the only record of "ended" (no status column). Sessions **restrict** deleting their role, access row or user: admin services must end and remove the affected sessions themselves, in the same transaction, publishing "session stopped" events through the outbox (Phase 5). A session is ACTIVE only if `IsActiveAt(now)` **and** the user, the access row and the application are active **and** the user still holds the session's role (directly or through a group); GetSession and token refresh must check all of it. Finished sessions (ended or expired) are deleted `Sessions:KeepFinishedFor` (default 7 days) after they finished, by `SessionCleanupService` (hourly, bulk delete), which also prunes OpenIddict's old tokens and authorizations with the same cutoff.
- Server keys (option A of docs/design/phase-3-openiddict.md): `KeyRing` generates, stores and rotates RSA signing and encryption keys in `server_keys`, encrypted with Data Protection, whose key ring is in `data_protection_keys`. Lifecycle (`KeyRotationPolicy`, pure): a new key every 30 days, published 1 day before use, used 30 days, kept 1 more day after its successor took over (counted from the takeover, not the key's age), then deleted. Outside Development/Testing, Data Protection's key ring must be encrypted with a certificate (`DataProtection:CertificatePath` + `DataProtection:PrivateKeyPath`, PEM files) or startup fails.
- OpenIddict (`Hosting/AuthServerSetup.cs`): endpoints `connect/authorize` and `connect/token` (passthrough), code+PKCE (**S256 only**: `plain` removed), client credentials, refresh; signed, unencrypted access tokens (10 min); refresh tokens 8 h (a session, and well inside key retention). Issuer from `Auth:Issuer` (required outside Development/Testing). Keys come from `KeyRing` through `ConfigureServerKeys`; `ServerKeyRefresher` loads them **before startup completes** (broken key storage stops startup), refreshes hourly (failures logged and retried) and resets OpenIddict's options cache so rotation needs no restart. Plain HTTP only with `OpenIddict:AllowInsecureHttpDevOnly=true`, which is refused outside Development/Testing.
- Client secret rotation (no downtime): `ApplicationService.RotateSecretAsync` keeps the previous secret working for `Applications:OldSecretValidFor` (default 7 days, must be positive): its hash (copied from OpenIddict's client, never plain text) and end live on `applications` (`old_secret_hash`, `old_secret_valid_until`, `ck_applications_old_secret`: both or neither). OpenIddict keeps one hash per client, so `KaleApplicationManager` (replaces OpenIddict's application manager) overrides `ValidateClientSecretAsync`: OpenIddict's check first, then the old hash with OpenIddict's own comparison (confidential clients only), logging a warning naming the application whenever the old one is used. Only one old secret is kept (a second rotation replaces it). Retire it at once with `RetireOldSecretAsync` (admin API `DELETE /applications/{id}/old-secret`, CLI `admin retire-old-secret <key>`, admin UI "Retire old secret"), or rotate with `retireOldSecret` (`POST /applications/{id}/secret` body `{ "retireOldSecret": true }`, CLI `rotate-secret <key> --retire-old`, the UI's box). `GetAsync` reports `OldSecretValidUntil` (null once over).
- Applications and OpenIddict clients: only `ApplicationService` creates/changes them, together in one transaction. Link = the generated column `openiddict_applications.application_key` (`split_part(client_id, '.', 1)`) with FK → `applications.key`, and the check `ck_openiddict_applications_client_id` allows only `client_id` = the key (the web client) or `{key}.desktop` (the desktop client), so at most these two per application (all immutable); OpenIddict stores only the secret hash. Every web client: confidential, code+PKCE, client credentials, refresh; redirect URIs absolute https (http only for localhost). `IsActive` lives only in `applications`; handlers enforce it. After registration the name and return addresses can change (`UpdateAsync`, application and client in one transaction; the secret and flows stay), the key never; `auth`'s return addresses are refused (they belong to the admin UI's deployment).
- Desktop sign-in (owner's decision, `Applications/DesktopClient.cs`): a desktop app (WPF) can't keep a secret, so it signs users in to its application as the **public** client `{key}.desktop` (keys can't contain `.`, so no collision) through the **system browser** (no embedded browser, never the app collecting the password): code + PKCE (S256) + refresh, no client credentials, return addresses `http://127.0.0.1/callback` and post-logout `http://127.0.0.1/signed-out` on **any port** (RFC 8252: OpenIddict 7.7 ignores the port of a loopback address for a client whose application type is `native`; scheme, host and path must match, so nothing else is accepted). `AuthorizeEndpoint`, the role picker and `TokenEndpoint` map the client id to its application (`DesktopClient.ApplicationKeyOf`): its tokens have `aud` = the application key (its own API accepts them as today) and its sessions are the application's, so the one-session rule holds across both clients (a desktop sign-in ends the user's web session of that application and the other way round). Off by default; switched on/off only by `ApplicationService.SetDesktopSignInAsync` (creates or deletes the client under the application's row lock; deleting it deletes its refresh tokens, so desktop users can't renew, their access tokens run out within 10 min), from the admin API (`PUT applications/{id}/desktop`, `{ enabled }`; `desktopSignIn` in the details), the admin UI (application page; turning off asks first) and `admin desktop-sign-in <key> on|off` (`register-app.sh --desktop`). Never for `auth`. Accepted trade-off of any public native client (RFC 8252 8.6): a program on the user's computer can start a sign-in to `{key}.desktop` and, while the browser's `kale.signin` cookie is valid, get a code on its own loopback port without the password, which also ends the user's other session in that application; only switch it on for applications that need it.
- Token audiences: a user's token has `aud` = the application key (also from the desktop client); an app's client-credentials token (to call AuthService) has `aud` = `urn:kale:auth-api`, which no key can equal (keys can't contain `:`), and no `sid`.
- gRPC API (`Grpc/`): registration, sessions, roles. Policy `AppCaller`: an app token (`aud` `urn:kale:auth-api`, `sub` = `client_id`, no `sid`); the caller's application comes from the token and must be active **on every call**; other applications' items are `NOT_FOUND`. `SessionCheck` holds the full ACTIVE definition (also for token refresh).
- Sign-in (`SignIn/`): ASP.NET Identity (`AddIdentityCore`, lockout 5 tries / 15 min, passwords ≥ 12 chars) with the `kale.signin` cookie (8 h, not sliding; apps never see it). `connect/authorize` → login page if needed → `UserSignIn.DecideAsync` (active application + active user + active access row; role = chosen, else default if eligible, else the only one) → code, which carries the role id (`TokenClaims.RoleId`, in the code only, never in a token). **No session yet:** any web page can send a signed-in browser to `connect/authorize`, so authorize changes nothing, and an unredeemed code leaves nothing behind. The session starts when the app redeems the code (`connect/token`, `authorization_code`): `UserSignIn.StartAsync` checks everything again with the code's role (lost access, a disabled user or application, or a role no longer held → `invalid_grant`; never another role) → `Session` (`Sessions:Lifetime`, default 8 h) → tokens with its `sid`. One open session per user and application: a new sign-in (another device, or a role switch) ends the user's earlier open sessions in that application through `SessionStopper` ("session stopped" events, in the same save as the new session), so their tokens stop working; sessions in other applications stay. Before reading them, `UserSignIn.StartAsync` locks, in this order: the user (`FOR SHARE`), the application's roles (`FOR KEY SHARE`, by id, the same order as `RoleEditor.DeleteAsync`, so a role switch and a role delete can't deadlock), then the access row (`user_applications`, `FOR UPDATE`), so two sign-ins of the same user to the same application take turns. Token claims: the access token only `sub`, `sid`, audience = app key (`TokenClaims.StartSession`, `ForSession` for test tokens); the ID token also `name` (display name) and `preferred_username` (user name), read from the database at every code exchange and refresh (`TokenClaims.SetUserNames`, ID token only), so applications can show who is signed in. Refresh goes through `SessionCheck`. Own password change (`/account/change-password`, linked from `/account/signed-in`; needs the `kale.signin` cookie): current password, new one twice. The current one is checked like a login (`CheckPasswordSignInAsync` with lockout, so wrong ones count); the new one goes through `UserPasswords` (the admin reset's rules: the user's open application sessions stop, so a stolen session doesn't outlive the old password). Then this browser's cookie is refreshed for the new security stamp (same expiry) and the page redirects to `?changed=true` (a reload doesn't post again). Identity's English reasons aren't shown: the page has its own TR/EN rules text. A user disabled since signing in is signed out instead.
- Role picker (`/account/select-role`): for several eligible roles without a usable default; the choice returns to the authorize request as `kale_role` (also usable by apps to switch roles), which `UserSignIn` re-checks. `prompt=none` → `login_required` / `account_selection_required`; `prompt=login` and `max_age` force a new login. `max_age` counts from when the password was entered (`SignInTime`, kept in the `kale.signin` cookie's properties, also the ID token's `auth_time`), not from the cookie's issue time, which Identity's stamp check renews every 30 min; a cookie without it counts as too old.
- Sign-out (`connect/endsession`): `id_token_hint` required (none or invalid → 400, against logout CSRF). A valid hint is enough to end the session it names (`sid`; others stay), with or without the `kale.signin` cookie, which often ends hours before the session. OpenIddict doesn't check the hint's lifetime (apps keep the ID token for the whole session) and ties it to the client: `client_id` must be among its audiences or presenters, or else the `post_logout_redirect_uri` must be registered for one of them. The `kale.signin` cookie is cleared only when it belongs to the hint's user. Redirects to a registered post-logout URI.
- User-facing pages are TR (default) and EN by `Accept-Language`; texts in `Resources/SharedText.{tr,en}.resx`; the HTML encoder allows all Unicode letters (special characters stay escaped). Pages use only `wwwroot/kale.css` and `wwwroot/kale-icon.svg`: no external fonts or scripts (isolated networks). They share `Pages/Shared/_Layout.cshtml` (head, the Kale brand, one card; each page sets `ViewData["Title"]`), styled like the admin UI in plain CSS, light or dark following the device.
- Auth.Client (`builder.AddKaleAuth<TOperations>()`, which reads everything from the `Kale` configuration section, including the secret file `Kale:ClientSecretFile`; `services.AddKaleAuth<TOperations>(options => ...)` underneath): JWT bearer validation against AuthService's JWKS (audience = the app key, type `at+jwt` only, claim names unmapped). `[Authorize(Enum...)]` → policy `kale-operations:{enum FullName}:{members}` (OR inside one attribute, AND across attributes); each request checks the session (cache 20 s) and the role's effective operations (cache 5 min), and fails closed if AuthService doesn't answer (5 s deadline). A refusal says why (`KaleAuthorizationResultHandler` reads the handler's `AuthorizationFailureReason`s): **401** (a challenge carrying `.error=invalid_token`, so OpenIddict's validation in the admin API answers 401 too) when the session is ended, not ACTIVE, unknown or its role is gone; **503** when AuthService is unreachable (`AuthServiceUnreachableException`, also `LookupTimeout`) and no cached answer can stand in; **403** when the role lacks the operation, for a token without `sid`, or when AuthService answers with an error (a refusal, not an outage). `AddKaleOperationAuthorization` replaces only ASP.NET Core's default result handler; startup fails (`ResultHandlerCheck`) if the app's own handler doesn't derive from Kale's. Kale.Auth.Web: a page challenged with that `invalid_token` marker is handled as a refused renewal, and `/auth/login` renews the token even while it's fresh (endpoint metadata `AsksKaleBeforeSignIn`), so an ended session found by any API (this project or another) leads to Kale's password page instead of bouncing back to the 401. Concurrent misses for one key share one lookup (`TimedCache`), which `SessionAccess` bounds itself (`LookupTimeout`, 5 s, also the gRPC deadline; AuthService's in-process lookups too); a request's own token ends only its wait, so an aborted request no longer cancels the lookup. The app calls AuthService with a client-credentials token, reused until 1 min before it expires, over one gRPC channel. Operations register in the background at startup and again every 5 min, retried with growing waits (max 30 s), except `INVALID_ARGUMENT` (logged, never sent again). Startup fails if an endpoint's `[Authorize]` uses another enum, or if `AllowInsecureHttpDevOnly` is set outside Development/Testing (checked when the connection is created, before anything is sent).
- Auth.Desktop (`Kale.Auth.Desktop`, for desktop apps; doesn't depend on Auth.Client): `new KaleDesktopSignIn(new KaleDesktopOptions { Authority, ApplicationKey })` (plain http only with `AllowInsecureHttpDevOnly`; it can't know the environment, so the app sets it only in development). `SignInAsync()` opens `connect/authorize` in the browser (`IBrowser`, default `SystemBrowser`: `Process.Start` with `UseShellExecute`; tests inject their own), waits (`SignInTimeout`, 5 min) on a `TcpListener` on 127.0.0.1 port 0 (not `HttpListener`: on Windows it needs admin rights for 127.0.0.1) for `/callback`, answers other paths 404, checks `state` before anything else, exchanges the code with the PKCE verifier (no secret) and answers the browser with a plain TR/EN page by `CurrentUICulture`. `GetAccessTokenAsync()` renews a minute before expiry, one renewal at a time (`SemaphoreSlim`; refresh tokens are single-use); `invalid_grant` forgets the tokens and throws `KaleSignInRequiredException`, other failures `HttpRequestException` (tokens kept). `SignOutAsync()` forgets the tokens, then opens `connect/endsession` (`id_token_hint`, `client_id`, no return address: Kale's signed-out page). Tokens in memory; optional `IRefreshTokenStore` (the docs suggest DPAPI, no dependency). `User` (sub, name, preferred_username) is read from the ID token without checking its signature (it came straight from the token endpoint; display only). `KaleBearerHandler` adds the token. Awaits use `ConfigureAwait(false)` (WPF UI thread).
- Auth.Web (`Kale.Auth.Web`, for a web application's server; doesn't depend on Auth.Client): `builder.AddKaleSignIn()` reads the same `Kale` section (Authority, ApplicationKey, ClientSecret / ClientSecretFile, AllowInsecureHttpDevOnly with the same Development/Testing rule); `app.MapKaleSignIn(prefix = "/auth")` adds `GET login?returnUrl=` (local paths only), `POST logout` (same origin only, else 403) and `GET me` (sub, name, preferred_username, or 401). Cookie (`KaleCookie`, named `kale.{key}`, httpOnly, SameSite=Lax, Secure outside Development/Testing, 8 h from sign-in, not sliding) + OpenID Connect (`KaleOpenIdConnect`: code + PKCE, query response mode, `openid offline_access`, claims unmapped). Sign-ins and their tokens live on the server (`SignInTicketStore`: the app's `IDistributedCache`, in memory unless it registers a shared one, encrypted with Data Protection); the cookie carries only a key (the tokens made it ~7 KB); a renewal reaches the store when its response starts, and the 30 s share covers the gap. `SignInCookieEvents.ValidatePrincipal` renews the access token when a minute or less is left (`TokenRenewal`: one call per refresh token, its answer shared for 30 s, Kale's reuse window); a refusal (4xx with an OAuth `error`) rejects the cookie and marks the request "session ended", and the next page navigation (also `/auth/login`, which renews even a fresh token, and a page challenged with Kale.Auth.Client's `invalid_token`) ends **only this application's sign-in** (owner's decision): it removes the cookie and goes to Kale with `prompt=login`, so Kale asks for the password (its own cookie mustn't silently sign back in and end the session on the other device) but keeps `kale.signin`, and the user's other applications keep single sign-on. A marker cookie `kale.{key}.ask-password` (same settings, 8 h, cleared by the next sign-in in `SigningIn` and by sign-out) keeps `prompt=login` if the user leaves Kale's page and comes back; it's a convenience, not a guarantee (a cleared cookie means a plain sign-in, which Kale allows). Its value is the ID token protected with Data Protection, so the user's own sign-out (`POST logout`), which signs out at Kale too (`connect/endsession` with the ID token), still reaches Kale after the session ended (shared computers). An admin's "stop session" therefore ends only that application's sign-in; to force the password everywhere, disable the user or change their password (security stamp). No usable answer keeps the user signed in. The endpoint metadata is read during authentication, so an app's explicit `app.UseRouting()` must come before `UseAuthentication()`. Not signed in: a fetch gets 401 (`Sec-Fetch-Mode`, else `Accept: text/html`), a page goes to Kale and comes back to itself (the cookie handler's `ReturnUrl`; every return address is checked with `SignInRules.IsLocalReturnUrl`, else `/`); forbidden is 403. A cookie request that isn't GET/HEAD/OPTIONS/TRACE counts as signed in only from the site's own origin (CSRF). `GetKaleAccessTokenAsync()` and `IHttpClientBuilder.AddKaleAccessToken()` give the user's token. Sign-in errors come back as `?kaleError=<code>`; a page that needs sign-in then answers 401 instead of asking Kale again (which would loop). With `AddKaleAuth` in the same project, the default scheme (unless the application set its own) is the policy scheme `KaleBearerOrCookie` (`Authorization: Bearer` → JWT bearer, else the cookie; set in `PostConfigure`, so call order doesn't matter), and `[Authorize(Operation)]` reads `sid` from either.
- Invalidation events (`Auth.Contracts/Protos/invalidation.proto`, protobuf `InvalidationEvent`, at-least-once): every change that must reach client caches adds an `outbox_messages` row (built by `Outbox/OutboxEvents`, with the session's or role's `application_id`; null for `UserDisabled`; deliberately no foreign key: a message records what happened rather than a relationship, both callers take the id from the row they just changed, and an FK would only prove the application exists, not that the payload's session or role belongs to it) in the **same `SaveChanges`** as the change. Saving the row is what sends the event (the trigger below); nothing reads or marks it afterwards, and `SessionCleanupService` deletes rows older than `OutboxCleanup.KeepFor` (1 day: nothing replays them, a reconnecting client clears its caches instead; the day is for looking into a recent problem in SQL). Sessions end only through `SessionStopper` (admin stop, sign-out, disabled user, new password), which queues `SessionStopped`; its `Stop(Session)` doesn't save, so a caller saves it with its own change. Roles change only through `RoleEditor` (create, rename, operations with `RoleEdited`, delete). Deleting a role locks it, stops its open sessions (`SessionStopped` each), removes all its sessions and clears it as a default role, in one transaction. `UserAccounts` disables a user and stops their open sessions (`UserDisabled` is for audit; clients act on the `SessionStopped` events). Row locks keep these consistent: `RoleEditor` locks the role (`FOR UPDATE`); `UserAccounts` locks the user (`FOR UPDATE`) and `UserSignIn` takes `FOR SHARE` on it before checking `IsActive`, so no session can start after a disable.
- Auth.Client's `InvalidationListener` (hosted, no settings of its own): keeps `InvalidationStream.Subscribe` open over the same gRPC connection as the lookups. Once the response headers carry AuthService's `Subscribed` marker it clears both caches (events sent while disconnected are lost) and sets `SessionAccess.ReceivingEvents`, which lets session status live 2 min instead of 20 s; any end of the stream clears that flag and it reconnects every 5 s (a refusal without the marker keeps the caches). `SessionStopped` evicts the session, `RoleEdited` the role; `UserDisabled` needs nothing. Unreadable events are logged and skipped. It warns at startup if the backchannel handler can't send HTTP/2 keep-alive pings (a silently dead connection would go unnoticed). Settings from older versions (`Kale:RabbitMq*`) are ignored.
- Invalidation stream: gRPC `InvalidationStream.Subscribe` (`invalidation_stream.proto`, server streaming of `InvalidationEvent`, policy `AppCaller`, application active at connect) sends a client app instance its own application's events only: `SessionStopped` for its sessions, `RoleEdited` for its roles, never `UserDisabled` (outbox rows with a null `application_id`). At least once; events saved while a client isn't connected are lost, so it clears its caches on every (re)connect, when the response headers arrive. Between Kale's instances: an `AFTER INSERT` trigger on `outbox_messages` (raw SQL in migration `InvalidationNotify`, noted in `OutboxMessageConfiguration`) calls `pg_notify('kale_invalidation', {"application_id", "event": payload in hex})`, delivered on commit in commit order (nothing for a rollback); the listener never reads the row. Each instance runs `InvalidationNotificationListener` (hosted): one dedicated unpooled Npgsql connection (`application_name` `Kale.AuthService invalidation listener`) that LISTENs, sends `SELECT 1` (5 s timeout) after 30 s without notifications to notice a dead connection, and reconnects by itself every 5 s. `InvalidationSubscribers` (singleton, one lock) holds this instance's streams: a stream registers **before** its response headers are sent, so nothing falls between "connected" and "listening"; subscribing is refused (`UNAVAILABLE`) while the listener isn't listening; losing the listener connection ends every stream, and so does shutdown, from `IHostApplicationLifetime.ApplicationStopping` (Kestrel stops before hosted services and would otherwise wait its whole shutdown timeout for the never-ending streams) (`UNAVAILABLE`, clients reconnect and clear caches); each stream has a bounded queue (1000 events) and is ended (`UNAVAILABLE`) when it overflows, so a slow client never blocks the others. An application deactivated while its stream is open: the stream re-checks the application before each batch of waiting events and ends with `PERMISSION_DENIED` (nothing is sent before that). Any other failure inside a stream (e.g. the database unreachable for that check) ends it with `UNAVAILABLE`, never `UNKNOWN`; the proto says any status but `PERMISSION_DENIED` means "reconnect". The listener's connection must reach PostgreSQL directly or through a **session**-pooling proxy, never a transaction-pooling one (e.g. PgBouncer in transaction mode): LISTEN belongs to the server session, which such a proxy shares between clients.
- Admin API (`Admin/AdminApi.cs`, `/admin/api`): AuthService is the application `auth` (`AuthApplication.Key`) with `AuthOperations.Admin`; every endpoint needs a **bearer** token (OpenIddict validation, audience `auth`; the sign-in cookie never counts, against CSRF) whose session holds `auth.Admin`, checked by Auth.Client's own `[Authorize]` with in-process lookups (`AdminSessionLookups`, only sessions and roles of `auth`). `AdminInvalidationFeed` feeds that cache from this instance's own `InvalidationSubscribers` (every application's events, in-process, through `InvalidationListener.TryApply`), so revoking admin rights takes effect right away. `AuthService admin bootstrap <user> <display-name> <admin-ui-redirect-uri> [<post-logout-uri>]` (password on stdin) checks everything first, then creates `auth`, registers its operations, the role `Admin` and the first admin, and prints the admin UI's client secret. Endpoints live in one file per area (`Admin/ApplicationEndpoints.cs`, ...) and change data only through the domain services; a `ValidationException` becomes a 400 problem response (`detail` = the reason) through the group's filter (`RefusalsAsProblems`). For an unknown id the services throw `NotFoundException` (also when the row is deleted between their check and their insert: the foreign-key violation is turned into one), which the filter answers with a 404; changing endpoints don't look the id up first, so input that is wrong in itself is a 400 even for an unknown id. `auth` can't be deactivated, and no change may leave nobody with `auth.Admin` (`LastAdminCheck`: some other active user with active access to `auth` must keep it, directly or through a group; `RoleEditor` asks before deleting a role of `auth` or taking `auth.Admin` from it, `UserAccounts` before disabling an admin; it takes one advisory lock inside the caller's transaction, so two such changes at once take turns). Access rows and direct roles change only through `UserAccess` (locks the user like `UserAccounts`; deactivating access stops the user's sessions in that application, unassigning a role stops its sessions unless a group still grants it; last-admin check on both). Groups change only through `GroupEditor` (adding a member locks the group `FOR SHARE`, then the user; adding a role locks the group, then its members; removing a member, a role or the group locks the group, then the affected users, then stops their sessions whose role they no longer hold, with the last-admin check). Users are created only through `UserCreator` (Identity's checks plus a display name, all problems in one `ValidationException`). Their names are corrected and users deleted only through `UserEditor` (locks the user like `UserAccounts`): a rename meets `UserCreator`'s rules (`NameProblemsAsync`), saves through Identity's `UpdateAsync` (new concurrency stamp) and keeps the security stamp and the sessions (ID tokens get the new `name`/`preferred_username` at the next refresh); a delete refuses the caller's own account and the last admin (`LastAdminCheck`), stops the open sessions (`SessionStopped`), deletes the user's sessions (they restrict the cascade), OpenIddict tokens and authorizations (by subject; no foreign key), then the user with a bulk delete (the database cascades access rows, direct roles, memberships, Identity rows). Passwords are set only through `UserPasswords` (`PUT /users/{id}/password`, the admin UI's "Set password", `admin set-password`): Identity's password rules (all problems in one `ValidationException`), a new hash, the lockout and failed count cleared, a new security stamp, and the user's open sessions in every application stopped, all in one save, with the user locked like `UserAccounts` (and read again under the lock); the answer never holds the password. The new stamp ends the old password's sign-ins at once: `connect/authorize` treats a `kale.signin` cookie with an older stamp as no sign-in (login page), and a code carries the stamp it was issued with (`TokenClaims.SecurityStamp`), which `UserSignIn.StartAsync` compares under its user lock, so a code issued before the change starts no session. The gRPC `RegisterOperations` refuses the caller `auth`: only AuthService registers `auth.*` (the admin UI's secret must not be able to make `auth.Admin` obsolete).
- Admin UI (`admin-ui/`, decision: Next.js BFF): signs in to `auth` with code + PKCE (`openid-client`); tokens stay on its server, in memory (`SessionStore`, 8 h, keyed by the httpOnly `kale_admin_session` cookie; a restart signs admins out). The decisions live in `src/lib/auth-flow.ts` (no Next.js, unit-tested); routes only wire them up. It calls `/admin/api` with the admin's bearer token (`AdminApiCaller`), renewing it a minute before expiry, once for parallel calls (refresh tokens are single-use); a refused refresh, a 401 or a 403 (session stopped, signed in elsewhere, `auth.Admin` taken away) drops the session (`SessionStore.end`, which keeps the id known as ended until its 8 h are over, so a reload, Back or another tab with the same cookie still gets "ended") and shows `/signed-out?state=session-ended`, whose link uses `prompt=login`: a plain sign-in would let AuthService's own cookie sign the admin straight back in and end the other device's session in turn (no session at all is a normal sign-in). Someone without `auth.Admin` gets no session: with no access to `auth` they land on `/not-admin`, otherwise their new AuthService session is ended at once and they land on `/signed-out?state=not-admin`; "another account" links use `prompt=login`. Sign-out is a form POST, refused (403) unless it comes from the UI's own origin (`Origin`/`Sec-Fetch-Site`), and also ends the AuthService session (`connect/endsession`). OIDC metadata is cached until a failure (`cacheUntilFailure`). Settings: `KALE_AUTH_ISSUER`, `KALE_ADMIN_UI_URL`, `KALE_ADMIN_CLIENT_SECRET_FILE`, `KALE_ENVIRONMENT`, `KALE_TIME_ZONE` (IANA name for the times shown, UTC when empty; an unknown one stops the server at startup, `src/instrumentation-node.ts`; compose takes `ADMIN_UI_TIME_ZONE`); plain http needs `KALE_ALLOW_INSECURE_HTTP_DEV_ONLY`, refused outside Development/Testing. Pages use system fonts and Tailwind CSS built into one local stylesheet, nothing from a CDN (isolated networks), no telemetry. Turkish by default, English by cookie (`/language?to=en`) or browser. `dev-stack.sh` runs `admin bootstrap` (first admin `ADMIN_USER`, password in Podman secret `kale_admin_password`, UI secret in `kale_admin_ui_client_secret`).
- Admin UI pages (one folder per area under `src/app`, e.g. `applications/`): the page (server component) reads through `adminApi`; changes are server actions (`actions.ts`) that start with `requireSameOrigin()` and return an `Outcome` (`src/lib/admin-requests.ts`: done, refused with AuthService's 400 `detail`, or 404) that the client form (`forms.tsx`, `useActionState`) shows; forms with typed input return `afterSubmit(outcome, submitted)`, so a refused form starts again from what was sent (React empties a form after its action). Pages under an application nest under it (`applications/[applicationId]/roles`). A page for one item reads it with `find` (404 → `undefined` → `notFound()`). A `<select>` whose default can change gets a `key` from that value (React applies a select's `defaultValue` only when it's created, and resets forms after actions). Passwords are sent as typed (not trimmed) and never come back in a form's state (`withoutPassword`). Each area's API calls and form parsing live in `src/lib/<area>.ts` (no Next.js, unit-tested with a fake `ApiCall`); ids in paths are escaped with `encodeURIComponent`. Hard-to-undo changes ask first (`ConfirmButton`, a confirmation dialog that submits the button's form); client secrets appear once (`OneTimeSecret`) and never in a URL. Other failures go to `app/error.tsx`. `test/messages.test.ts` keeps `tr.json` and `en.json` on the same keys.
- Admin UI design (owner's decision): Tailwind CSS 4 with our own small components in `src/components/ui` (shadcn/ui style) on MIT libraries: Radix UI (dialogs, confirmations, popovers), TanStack Table 9 (`DataTable`: search, sorting, paging in the browser), cmdk (`MultiSelect`), lucide-react icons. **Not PrimeReact/PrimeIcons**: from v11/v8 they are proprietary (PrimeUI License, paid per developer, license key). Lists are `DataTable`s, defined in client components (columns hold functions, which a server page can't pass). "New …" forms open in a `Dialog` that closes on success and stays open with the reason after a refusal; creating a user or group opens its page. Picking several items (roles for a user or group, members, a role's operations) is a `PickDialog`: the `MultiSelect` posts one hidden field per pick, read with `listFromForm`, and the action applies them one by one with `changeEach` (stops at the first refusal). Sign-in, sign-out and error pages outside a session (`AppShell`'s public pages) get no menu.
- Test tokens (Development/Testing only; `Tokens/TestTokens.cs`): the admin UI's **Test token** page asks `connect/token` with the custom grant `urn:kale:params:oauth:grant-type:test-token`, its own client credentials, and the admin's access token as the bearer (the same `auth.Admin` check as the admin API). - Local gRPC uses h2c inside compose, and published on `APP_BIND_ADDRESS` (127.0.0.1) for an application a developer runs with `dotnet run` (owner's decision; still Development only), behind `Grpc:AllowInsecureDevOnly`. TLS is supported. Without TLS, Kestrel speaks HTTP/2 only on an endpoint limited to it, so local setups add one in configuration (`Kestrel:Endpoints:GrpcDevOnly:Url=http://+:8081`, `:Protocols=Http2`); AuthService refuses such an endpoint (or `Kestrel:EndpointDefaults:Protocols=Http2`, which also reaches `ASPNETCORE_URLS` addresses) without the flag, and the flag outside Development/Testing. ## PR review
After opening or updating a PR, run the **`pr-reviewer`** agent ([.claude/agents/pr-reviewer.md](.claude/agents/pr-reviewer.md)) with the PR number. It builds and tests the PR in a temporary worktree (skipped for docs/config-only PRs and never done for PRs from forks; the review says when it skipped), checks it against `main`'s version of this file and DESIGN.md, and posts its concerns on the PR as a `COMMENT` review. Fix its **blocking** items (or reply on the PR explaining why not) before asking for a human review.
